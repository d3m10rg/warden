# Roadmap

## 0.1 — наблюдение

TUI/CLI, совместимость с установленным контроллером v1 без изменения его кода,
AWG/WG и отдельные peer, компоненты VLESS, SQLite на 48 часов, история и трафик.
Пассивный режим: никаких ping, HTTPS-проб Warden, изменений сети или автолечения.
Установка из GitHub выполняется владельцем.

## 0.2 — расширенная диагностика

Внешняя/внутренняя связность, HTTPS через определённый канал, ограниченный iperf3
до подготовленного сервера, безопасный отчёт doctor. Все проверки по запросу,
с проверкой маршрута и лимитами нагрузки. Пробы не изменяют решение контроллера.

Реализация 0.2.0: ASCII-панели TUI, отдельная вкладка Diagnostics, предпросмотр и
подтверждение, IPv4 ping, один HTTPS target из установленного контроллера,
iperf3 с ограничением нагрузки и doctor. Результаты проверок остаются в текущем
сеансе/выводе CLI; их сохранение в SQLite не входит в эту версию. Сервер iperf3
готовится отдельно владельцем. Автоматический запуск проверок отсутствует.

## 0.3 — клиенты VLESS

Список клиентов, выдача и обновление подписок, добавление, перевыпуск UUID и
удаление через механизм `manage-ravelin-vless-ws-users.sh`. Меню Clients и CLI,
предпросмотр и подтверждение, сохранение стабильного источника и меток учёта.
URL подписки сохраняется при ротации. Сборщик остаётся пассивным.
Наблюдение транспорта и подробных результатов проб установленного контроллера v2.

## 0.4 — управление каналами

0.4.0/0.4.1: смена rank включённого канала через установленный `forpostctl set-priority`.
Клавиша p в Tunnels, CLI priority, предпросмотр, подтверждение, повторная проверка
реестра, сохранение SSH_CONNECTION, вывод manifest и откат средствами backend.
Maintenance реализован в 0.5.0; Stopped/Start — в 0.6.0;
реализация первого шага не означает готовность всех операций этого раздела.

Использование установленного `forpostctl` и реестра v2 с отдельной приёмкой
операций из Warden. Повторная миграция работающего контроллера не требуется. Приоритеты,
Maintenance, Stopped, запуск и возврат в выбор. Состояния сохраняются после reboot.
Общая блокировка, предпросмотр, журнал операции, откат, защита последнего выхода.
Постоянные туннели остаются только для наблюдения/диагностики.

## 0.5 — Maintenance

Исключение из выбора с сохранением туннеля; возврат после HTTPS-проверки.
Используется транзакционный backend установленного forpostctl без его перезаписи,
с общей блокировкой, manifest/rollback и проверкой реестра под блокировкой.
Защита последнего включённого и последнего здорового выхода; поддержка WSS
в наблюдении. Приёмка на Ravelin отдельно, сначала на резервном канале.

## 0.6 — Stop/Start

Остановка только заранее исключённого канала в Maintenance с исправным другим
выходом. AWG и транспорт останавливаются отдельно; marker и systemd condition
сохраняют Stop после запросов контроллера и reboot. Start восстанавливает транспорт,
AWG и собственные маршруты проб, проверяет HTTPS и оставляет Maintenance.
Возврат в автоматический выбор — отдельное действие. Общий journal/rollback,
проверка неизменности конфигов и отказ при неизвестных зависимостях.
Linux CI проверяет код и condition; приёмка на Ravelin и reboot — отдельно владельцем.

## 1.0 — стабильная эксплуатация

Завершённая приёмка на Linux и Ravelin, измеренная нагрузка, проверенные обновление
и откат. Версионированная поставка через GitHub. Миграции сетевого backend отделены
от обновления Warden; автообновлений нет.

После 1.0 по отдельному решению: клиентская проверка VLESS, IPsec SA, интеграция
метрик с существующим мониторингом. Веб-интерфейс, собственные
Telegram-алерты и развёртывание Forpost не входят в текущий roadmap.
