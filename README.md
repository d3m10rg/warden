# Warden 0.2.0

Локальная консоль наблюдения за VPN-туннелями и компонентами VLESS на Ravelin.
Полноэкранный интерфейс в стиле CPView, командный режим и история за последние
48 часов. **Warden не меняет маршрутизацию и конфигурацию VPN.** Сборщик пассивен;
диагностика 0.2 отправляет пакеты только после явного запуска.

```text
+- WARDEN 0.2.0 | DEMO | age 0s | FRESH --------------------------------------+
| [1 Overview]  2 Tunnels   3 Hosts   4 VLESS                                 |
|  5 Traffic   6 Events   7 Diagnostics                                       |
+-----------------------------------------------------------------------------+
+- EGRESS / CONTROLLER -------------------------------------------------------+
| Active: secondary    Backend: controller-v1    Probes fresh: True           |
| Unreachable guard: True    Local source rule: True                          |
+-----------------------------------------------------------------------------+
+- TUNNELS -------------------------------------------------------------------+
|   Tunnel       Interface  Role    Health        RX bit/s    TX bit/s        |
|   ------------ ---------- ------- ----------- ----------- -----------       |
|   secondary    awgfp0     Active  Healthy        1.2Mib/s  410.2Kib/s       |
|   primary      awgfp1     None    Down             0.0b/s      0.0b/s       |
+-----------------------------------------------------------------------------+
+- SERVICES ------------------------------------------------------------------+
| sing-box-vless-ws.service                    | Running                      |
| nginx.service                                | Running                      |
+-----------------------------------------------------------------------------+
+- NOTICES -------------------------------------------------------------------+
| DEMO: synthetic data; no commands executed                                  |
+-----------------------------------------------------------------------------+



+- Overview | lines 1-17/17 --------------------------------------------------+
| 1-7/Tab: view | arrows: select/scroll | Enter: details                      |
| PgUp/PgDn: scroll | Esc: back/cancel | q: quit                              |

```

## Что входит

- Выбор Active по реальному маршруту table 10400, а не по handshake.
- Чтение literal `PATHS` установленного контроллера v1 через AST, **без импорта
  и выполнения его кода**. Также поддерживается чтение реестра каналов v2.
- Healthy/Degraded/Down по существующим HTTPS-пробам контроллера; отдельные
  признаки устаревания данных, расхождений маршрута и отсутствующих guards.
- Обнаружение AWG/WG, статистика интерфейса и каждого peer. Дополнительный peer
  без handshake не делает весь постоянный туннель Down.
- RX/TX, скорость по двум измерениям, объёмы за 1 минуту, 1 час и сутки.
- Наблюдаемое время исправности Forpost и нахождения в роли Active.
- История состояния, обновлений handshake, разрывов измерений и переключений.
- Состояние sing-box, Nginx, failover, экспортера, алертов; краткие данные VLESS
  без UUID, имён пользователей и WebSocket-пути; проверка наличия TCP listener.
- JSON для командного использования, поддержка `warden -status` / `warden -list`.

В 0.2 добавлены ручные ping, HTTPS, iperf3 и пассивный doctor. Приоритеты,
отключение каналов и перезапуски VPN остаются вне этой версии. Hosts показывает
наблюдаемые адреса; результаты ручных проверок — во вкладке Diagnostics.
IPsec представлен только состоянием службы; диагностика SA пока не реализована.
См. [roadmap](docs/roadmap.md).

## Требования

- Linux, Python **3.9+** с `curses` и `sqlite3`, systemd, iproute2 (`ip`, `ss`),
  `awg` или `wg`. Debian 13/Python 3.13 — целевая среда Ravelin.
- Python-зависимостей из pip нет. Установщик ничего не скачивает и не устанавливает
  системные пакеты. `forpostctl`, Prometheus и доступ к Monitoring не требуются.
- Запуск от root: AWG и системная конфигурация требуют соответствующих прав.
  SQLite и локальная конфигурация доступны только root; TUI не открывает сетевой порт.
- Поддерживается существующая IPv4-схема защищённого выхода table 10400,
  source `10.78.254.2`, правило 99 с `iif lo`. Warden сообщает отклонения, не исправляет их.

## Сначала посмотреть без установки

На Ravelin, из root-сессии:

```bash
git clone https://github.com/d3m10rg/warden.git /root/warden
cd /root/warden
git checkout v0.2.0
python3 -B bin/warden --demo
python3 -B bin/warden status --live
```

Demo использует синтетические данные и не читает состояние сервера. `status --live`
выполняет только чтение; не создаёт базу, не запускает службы и не отправляет пробы.
Без TTY команда без аргументов выводит текстовый статус вместо TUI.

## Установка (выполняет администратор)

Из проверенного checkout `/root/warden`:

```bash
sh install.sh
systemctl status warden-collector.service --no-pager
warden status
warden
```

Установщик копирует код в `/opt/warden`, создаёт `/usr/local/bin/warden`, настройки
`/etc/warden/config.json`, `/var/lib/warden` и **только** `warden-collector.service`.
Он выполняет `systemctl daemon-reload` и включает/запускает Warden. Службы VPN,
контроллер, Nginx, firewall и их конфигурации не изменяются. Каталог `/opt/warden`
без маркера установки не перезаписывается.

Collector опрашивает состояние приблизительно раз в 10 секунд. Скорость появляется
после двух последовательных измерений; полный час/сутки — после накопления данных.
TUI перечитывает готовый снимок из базы, не создавая дополнительных фоновых проб.
Если сборщика нет, показывается один текущий снимок; он со временем станет STALE.

## Команды

```bash
warden                         # TUI
warden status                  # сохранённый снимок; без БД — текущее чтение
warden status --live            # принудительное чтение системы, без записи истории
warden status --json
warden list
warden show primary
warden show awg0                # peer_id и детали постоянного туннеля
warden traffic secondary --window 1m
warden traffic secondary --window 1h --json
warden traffic secondary --window 24h
warden traffic awg0/PEER_ID --window 1h
warden history --since 48h
warden history primary --since 2h
```

Глобальные параметры ставятся перед подкомандой:

```bash
warden --config /etc/warden/config.json status
warden --database /var/lib/warden/warden.sqlite3 history --json
```

`collect` и `collect --once` записывают **только историю Warden**; не запускайте их
параллельно службе. Файловая блокировка не допускает второго сборщика той же БД.
Коды возврата: 0 — команда выполнена (включая наблюдаемый Down в status);
1 — ручная проверка не прошла/не получила ответ; 2 — ошибка команды/предпроверки;
130 — прерывание. Подробная причина доступна в JSON.

TUI: `1–7`, Tab и горизонтальные стрелки — вкладки; вертикальные стрелки — выбор
туннеля/прокрутка; Enter — подробности; Esc — назад; PgUp/PgDn — прокрутка; q — выход.
Английские короткие статусы используются для компактного терминального отображения.

## Диагностика 0.2

Открытие вкладки и команды status/list/show остаются пассивными. Проверки не
влияют на статус controller health, приоритеты или маршруты. Их результаты
хранятся только в текущем TUI-сеансе/выводе CLI; SQLite остаётся базой наблюдений.
Нет фонового расписания, DNS-запросов, proxy, перенаправлений HTTP и установки пакетов.

```bash
warden doctor --json                         # только чтение, без адресов/секретов
warden ping secondary --scope internal       # предпросмотр, без пакетов
warden ping secondary --scope internal --run # 3 пакета, дедлайн 5 секунд
warden ping secondary --scope external --run
warden https secondary                      # предпросмотр привязки к каналу
warden https secondary --run --json          # один HTTPS target из контроллера
warden speed secondary                      # пока нет настройки — объяснит причину
warden speed secondary --run                 # 5 секунд, 5 Mbit/s, upload
warden speed secondary --seconds 5 --mbps 3 --reverse --run
```

CLI без `--run` проверяет маршрут и показывает план. Во вкладке `7 Diagnostics`
стрелки выбирают туннель; `i`/`e` — внутренний/внешний ping, `h` — HTTPS,
`s` — скорость, `d` — doctor. После предпросмотра `y` запускает проверку, `Esc`
отменяет. Обновления наблюдений продолжаются во время проверки. Выход закрывает
дочерний процесс проверки. Повторной проверки автоматически не будет.

Перед выполнением заново читаются live-данные и маршрут с source и oif.
В TUI изменение подтверждённого плана требует нового предпросмотра. Сокеты
привязаны к интерфейсу; для HTTPS также используются SOURCE, mark и probe table
установленного контроллера, проверяется unreachable default. При несовпадении —
отказ, без резервной отправки через другой канал. Конфигурация контроллера читается
как literal AST, не исполняется. Проверка HTTPS использует первый TARGETS,
проверяет сертификат/SNI и HTTP 200, бюджет 5 секунд и до 1024 байт ответа.
Это диагностика одной цели, не полный алгоритм health контроллера и не VLESS-сеанс.

Внутренний ping использует локальный адрес туннеля и peer. Внешний — публичный IP
канала через текущий физический/нетуннельный маршрут. `Reachable` означает ответ
на ICMP; `No reply` не доказывает недоступность хоста (ICMP может быть запрещён).
Показываются RTT и потери; ошибки инструмента/маршрута отделены от отсутствия ответа.

Для постоянного туннеля задайте точные цели: Warden не угадывает обязательный peer
по AllowedIPs. В существующий `/etc/warden/config.json` можно добавить раздел
(адреса ниже — примеры, **замените своими**):

```json
"diagnostics": {
  "awg0": {"internal": "10.90.0.1", "external": "192.0.2.20"},
  "secondary": {"speed_host": "10.90.1.1", "speed_port": 5201}
}
```

Для Forpost внутренний/внешний адрес уже читается из контроллера; можно явно
переопределить цели в diagnostics. HTTPS предназначен для каналов контроллера;
постоянные туннели поддерживают ping и подготовленный iperf3 без failover-управления.
Изменения diagnostics читаются при каждой проверке, перезапуск службы не нужен.

iperf3 требует **отдельно подготовленный сервер** за туннелем и установленный
локальный клиент с `--bind-dev`. Пока сервера нет, speed_host не задавайте.
Параметры: один TCP-поток, 1–10 секунд, целевая скорость 1–10 Mbit/s, upload или
`--reverse` download. По умолчанию около 3.1 MB полезной нагрузки за 5 секунд;
служебный трафик и особенности TCP добавляют расход. Это измерение при ограничении
нагрузки, не максимальная ёмкость канала. При неподдерживаемых опциях нет повторного
запуска без привязки/лимитов. Одновременно разрешена одна проверка Warden (блокировка
`/run/warden-diagnostics.lock`); сетевые проверки не запускаются из collector.

Для ping нужен iputils-ping, для скорости — iperf3. Установщик не добавляет их
автоматически; отсутствие этих опциональных инструментов не мешает наблюдению.
Doctor выдаёт allowlist состояний компонентов и наличия инструментов, без адресов,
peer ID, путей конфигурации, журналов, пользовательских имён и учётных данных.

Справочники реализации: [iperf3](https://software.es.net/iperf/invoking.html),
[iputils ping](https://github.com/iputils/iputils/blob/master/doc/ping.xml).

## Настройки и границы наблюдения

`config.example.json` содержит только отображаемые названия. `names` и `notes`
задаются по ID канала или интерфейсу; `peer_names` — по отображаемому `peer_id`.
Причина вроде блокировки провайдером — комментарий администратора, не автоматический
диагноз Warden. Изменение настроек применяется после перезапуска только сборщика:

```bash
systemctl restart warden-collector.service
```

Необязательные пути: `engine`, `registry`, `health`, `vless`, `database` (абсолютные).
При другом пути БД нужно также адаптировать systemd `ReadWritePaths`. Не указывайте
общедоступные каталоги: отчёт содержит сетевые адреса и операционную информацию.

- `Active` — выбранный маршрут, не гарантия исправности. `Active + Degraded` допустим
  во время подтверждения отказа. Числовой rank для v1 неизвестен (`null`): Warden не
  выдумывает приоритеты, отсутствующие в конфигурации старого контроллера.
- `Observed` у постоянного туннеля означает наличие свежего handshake хотя бы у
  одного peer. Какие peer обязательны, Warden не угадывает. Связность проверяется вручную.
- Свежесть handshake по умолчанию 180 секунд — диагностический признак; Forpost
  оценивается по HTTPS-результатам контроллера с возрастом не более 30 секунд.
- Состояние контроллера проверяется с учётом Linux boot ID и монотонного времени.
  Снимки старше 30 секунд помечены STALE; время перед началом наблюдения неизвестно.
- Направления RX/TX относительно Ravelin. Интерфейс и peer — разные источники
  счётчиков; их нельзя суммировать между собой. Трафик туннеля не равен трафику VLESS.
- Объёмы вычисляются по разностям счётчиков. Пропуски >30 секунд, reboot, смена
  идентичности или endpoint, скачок часов и сброс счётчика дают разрыв, а не ноль.
  Неполное покрытие показывается в процентах; дробная граница окна оценивается
  пропорционально интервалу и помечается `boundary_estimated`.
- История handshake — обнаруженные изменения последнего timestamp, не перехват
  каждого обмена. Переключения читаются из journal контроллера (до 500 за чтение,
  с cursor и дедупликацией). При отсутствии/ротации журнала полнота не гарантируется
  и отмечается предупреждением. Изменения роли между опросами могут быть пропущены.
- Полный клиентский сеанс VLESS и TLS Nginx не проверяются. Наличие listener и
  запущенной службы не заменяет такую проверку.

## История, нагрузка и отказ Warden

Сборщик пишет один актуальный JSON-снимок, компактные строки счётчиков и события
в SQLite WAL. Измерения и события удаляются по возрасту 48 часов приблизительно
раз в минуту во время работы сборщика. Существующий journal и чужие БД не очищаются.
База повторно использует свободные страницы; размер файла не обязан уменьшаться.
Основная БД ограничена 256 MiB при стандартной странице 4 KiB; WAL имеет отдельный
лимит сохраняемого журнала 8 MiB (во время транзакции может временно превышаться).

Служба имеет низкий CPU/I/O-приоритет, CPUQuota=20%, MemoryMax=128M, запрет записи
в системные файлы и запрет AF_INET/AF_INET6. AF_UNIX/AF_NETLINK оставлены для systemd,
`ss`, `ip`, AWG/WG. Это ограничители, **не результаты измерения нагрузки на Ravelin**.
Ошибка/переполнение БД остановит сборщик с видимой ошибкой; systemd попробует его
перезапустить. VPN и failover продолжают работу независимо, `status --live` доступен.

## Обновление и возврат версии

Автообновления нет. Сначала прочитайте изменения релиза; затем из `/root/warden`:

CI создаёт тег `v<версия>` для проверенного коммита main после успешных тестов;
существующие теги никогда не перемещаются. Это публикация версии в GitHub,
а установка на сервер всегда остаётся ручной.

```bash
git fetch --tags origin
git checkout <проверенный-тег>
sh install.sh
warden --version
systemctl status warden-collector.service --no-pager
```

Установщик сохраняет `/etc/warden/config.json` и БД, перезапуская только Warden.
Возврат к предыдущему **совместимому со схемой БД** тегу — той же процедурой.
Перед возвратом на 0.1 удалите добавленный раздел `diagnostics` из config.json:
старая версия отклоняет неизвестные поля; остальные настройки/БД сохраните.
Схема БД 0.1/0.2 имеет версию 1; неизвестная версия отклоняется без автоматической
миграции. Прерванную установку повторите из целого проверенного checkout; до этого
сборщик может оставаться остановленным. Файлы VPN восстанавливать не требуется.

Временное отключение Warden:

```bash
systemctl disable --now warden-collector.service
```

## Проверка перед использованием

```bash
python3 -B -m unittest discover -s tests -v
sh -n install.sh
```

GitHub Actions выполняет тесты на Linux/Python 3.9 и 3.13, curses в псевдотерминале,
проверку unit, один пассивный цикл сборщика и реальные route/mark/guard/ping
в отдельном Linux network namespace без доступа к сети Ravelin. Результат CI доступен во вкладке Actions.
Испытания на действующем Ravelin и измерение его нагрузки выполняет владелец после
установки. Порядок: `status --live` → установка → два цикла → сверка маршрута и
счётчиков → наблюдение нагрузки → остановка Warden и проверка независимости VPN.

Репозиторий не содержит конфигураций пользователей, приватных ключей, токенов,
реальных публичных endpoint и дампов серверов. В demo используются тестовые адреса.
