# Warden 0.5.0

Локальная консоль наблюдения за VPN-туннелями и компонентами VLESS на Ravelin.
Полноэкранный интерфейс в стиле CPView, командный режим и история за последние
48 часов, управление клиентами VLESS через существующий механизм подписок.
Сборщик пассивен; диагностика отправляет пакеты только после явного запуска.
Клиентские операции применяются только по подтверждению. Маршрутизация,
AWG и управление каналами остаются у `forpostctl` и установленного контроллера.

```text
+- WARDEN 0.5.0 | DEMO | age 0s | FRESH --------------------------------------+
| [1 Overview]  2 Tunnels   3 Hosts   4 VLESS                                 |
|  5 Traffic   6 Events   7 Diagnostics   8 Clients                            |
+-----------------------------------------------------------------------------+
+- EGRESS / CONTROLLER -------------------------------------------------------+
| Active: secondary    Backend: controller-v1    Probes fresh: True           |
| Unreachable guard: True    Local source rule: True                          |
+-----------------------------------------------------------------------------+
+- TUNNELS -------------------------------------------------------------------+
|   Tunnel       Interface  Role    Health        RX bit/s    TX bit/s        |
|   ------------ ---------- ------- ----------- ----------- -----------       |
|   secondary    awgfp0     Active  Healthy        1.2Mib/s  410.2Kib/s       |
|   primary      awgfp1     None    Down             0.0b/s      0.0b/s       |
+-----------------------------------------------------------------------------+
+- SERVICES ------------------------------------------------------------------+
| sing-box-vless-ws.service                    | Running                      |
| nginx.service                                | Running                      |
+-----------------------------------------------------------------------------+
+- NOTICES -------------------------------------------------------------------+
| DEMO: synthetic data; no commands executed                                  |
+-----------------------------------------------------------------------------+



+- Overview | lines 1-17/17 --------------------------------------------------+
| 1-8/Tab: view | arrows: move | Enter: details/menu                          |
| PgUp/PgDn: scroll | Esc: back/cancel | q: quit                              |
+-----------------------------------------------------------------------------+
```

## Что входит

- Выбор Active по реальному маршруту table 10400, а не по handshake.
- Чтение literal `PATHS` установленного контроллера v1 через AST, **без импорта
  и выполнения его кода**. Также поддерживается чтение реестра каналов v2.
- Healthy/Degraded/Down по существующим HTTPS-пробам контроллера; отдельные
  признаки устаревания данных, расхождений маршрута и отсутствующих guards.
- Обнаружение AWG/WG, статистика интерфейса и каждого peer. Дополнительный peer
  без handshake не делает весь постоянный туннель Down.
- RX/TX, скорость по двум измерениям, объёмы за 1 минуту, 1 час и сутки.
- Наблюдаемое время исправности Forpost и нахождения в роли Active.
- История состояния, обновлений handshake, разрывов измерений и переключений.
- Состояние sing-box, Nginx, failover, экспортера, алертов; краткие данные VLESS
  без UUID, имён пользователей и WebSocket-пути; проверка наличия TCP listener.
- JSON для командного использования, поддержка `warden -status` / `warden -list`.

В 0.2 добавлены ручные ping, HTTPS, iperf3 и пассивный doctor. В 0.3 добавлено
управление клиентами VLESS. В 0.4 добавлена смена приоритетов через установленный
`forpostctl`; отключение каналов пока выполняется отдельно. Hosts показывает
наблюдаемые адреса; результаты ручных проверок — во вкладке Diagnostics.
IPsec представлен только состоянием службы; диагностика SA пока не реализована.
См. [roadmap](docs/roadmap.md).

## Требования

- Linux, Python **3.9+** с `curses` и `sqlite3`, systemd, iproute2 (`ip`, `ss`),
  `awg` или `wg`. Debian 13/Python 3.13 — целевая среда Ravelin.
- Python-зависимостей из pip нет. Установщик ничего не скачивает и не устанавливает
  системные пакеты. `forpostctl`, Prometheus и доступ к Monitoring не требуются.
- Запуск от root: AWG и системная конфигурация требуют соответствующих прав.
  SQLite и локальная конфигурация доступны только root; TUI не открывает сетевой порт.
- Поддерживается существующая IPv4-схема защищённого выхода table 10400,
  source `10.78.254.2`, правило 99 с `iif lo`. Warden сообщает отклонения, не исправляет их.

## Приоритеты каналов — 0.4.1

В **2 Tunnels** выберите канал стрелками и нажмите **p**. Введите свободное
положительное число → Enter → проверьте план → **y**. Меньший приоритет
предпочтительнее. Результат и путь manifest backend отображаются в общей рамке.
Esc/n отменяет ещё не начатую операцию; запущенная операция завершается до выхода.

```bash
warden priority primary 15         # только предпросмотр, пример свободного rank
warden priority primary 15 --run   # явное применение через forpostctl
```

Warden читает реестр v2 и перед запуском повторяет проверку плана; изменение
реестра с момента предпросмотра отклоняется. Сам backend повторно валидирует
реестр под своей блокировкой. Внешние операции после повторной проверки остаются
под контролем backend; Warden не резервирует приоритет на время подтверждения.
Занятые rank, выключенные/retired каналы, постоянные туннели, другой путь реестра
и demo отклоняются. Уже установленный rank допустим: backend выполняет no-op.

Требуется `/usr/local/sbin/forpostctl` и root. Начиная с 0.4.2 обычный запуск
`sudo -i` → `warden` поддерживается без ручной передачи SSH-переменных. Если
`SSH_CONNECTION` отсутствует, Warden ищет живой TCP-сокет ближайшего sshd/sshd-session
в своей цепочке родительских процессов через `/proc`. Поддерживаются IPv4 и
IPv4-mapped IPv6 sockets. При наличии переменная валидируется и сохраняется.
Backend по-прежнему проверяет обратный маршрут SSH. История входов, произвольная
чужая сессия и фиксированный IP для определения адреса не используются.
При неоднозначности, локальной консоли, IPv6-only или отсоединённой цепочке
tmux/screen без SSH_CONNECTION применение отклоняется с объяснением.
Автоматического обхода через `--console` нет. Новая версия forpostctl не поставляется
и поверх установленной не копируется. Collector административные команды не вызывает.

Штатный `forpostctl set-priority` кратко останавливает selector, обновляет реестр
и его systemd units, затем восстанавливает timer; AWG и sing-box эта операция
не перезапускает. Выбор выхода продолжает выполнять контроллер с обычной проверкой
здоровья и задержкой возврата. Изменение rank может привести к переключению egress
и повлиять на текущие соединения. Успех записи rank не означает немедленное переключение.
Общая блокировка, manifest и автоматический откат принадлежат forpostctl.
При ошибке смотрите его вывод; Warden не делает автоматический повтор/второй откат.

## Maintenance — 0.5.0

В **2 Tunnels** выберите канал и нажмите **m**: предпросмотр → **y**. Если канал
уже в Maintenance, та же клавиша возвращает его в выбор. CLI:

```bash
warden maintenance secondary on         # только план, без проб и изменений
warden maintenance secondary on --run   # исключить, сохранив туннель
warden maintenance secondary off --run  # проверить и вернуть в выбор
```

Maintenance сохраняется в реестре v2 как `enabled=false, maintenance=true` после
reboot. Канал остаётся поднятым, доступны peer/handshake/счётчики и ручная диагностика.
Автоматические HTTPS-пробы контроллера для него прекращаются, Health становится
Unknown; это не означает остановку интерфейса. Role показывает Maintenance.
Добавленные, но ещё не введённые в работу Disabled-кандидаты этим режимом не включаются.

Применение выполняет расширение `warden/maintenance_backend.py`, загружающее
**установленный** root-owned forpostctl.py. Оно использует его runtime, общую
блокировку и change/switch/rollback, а не заменяет код forpostctl или контроллера.
Исходники backend и их родительские каталоги должны быть root-owned и недоступны
для записи группе/остальным. При несовместимой установке применение отклоняется.
После захвата общей блокировки hash реестра повторно сравнивается с предпросмотром.

Перед исключением нужен другой включённый канал. В транзакции selector останавливается,
выполняются свежие штатные HTTPS-пробы, проверяется здоровый альтернативный выход.
Если исключается активный канал, маршрут сразу переводится на здоровый резерв с
наименьшим rank. Это административное переключение: соединения могут прерваться.
Если исключается резерв, текущий выбранный выход должен пройти свежую проверку.
Последний включённый или единственный здоровый канал исключить нельзя; при all-down
операция отклоняется. Результаты в кеше или свежий handshake сами по себе не подходят.

При возврате сначала выполняется штатная HTTPS-проверка канала и проверяется,
что его rank свободен. Затем enabled восстанавливается; приоритет не меняется.
Маршрут напрямую не переключается: контроллер применяет свою обычную задержку
возврата после успешных наблюдений. Проверяются unreachable, правило 99 iif lo,
VLESS source/marks и административный маршрут средствами установленного backend.
При ошибке после начала транзакции применяется его журналируемый откат; Warden
показывает manifest и не повторяет изменение автоматически.

AWG, WSS/udp2raw, их keys/config/MTU/buffers и probe-reply rules не меняются и не
перезапускаются. Служба WSS определяется из transport.kind=wss и показывается как
forpost-wss-<interface>.service, независимо от старого имени ICMP-сервиса.
Внешний `forpostctl set-priority --enable` также может вернуть канал; если enabled=true,
оставшийся maintenance-marker не заставляет Warden считать его исключённым.
Stop/Start туннеля остаются отдельным следующим этапом.

## Клиенты VLESS — 0.3

В TUI откройте **8 Clients**. Выберите клиента стрелками **Up/Down**:
**Enter/s** — ссылки и обновление подписок, **a** — добавить,
**r** — перевыпустить UUID, **d** — удалить. Для нового клиента вводится только имя.
План показывается в панели подтверждения: **y** применяет, **n/Esc** отменяет.
Результат и ссылки отображаются в общей рамке, с прокруткой PgUp/PgDn.
**Esc** скрывает результат, переключение вкладки также очищает ссылки из состояния
экрана. Отдельный вход в ту же вкладку — `warden clients`.

В 0.3.1 убран переход из curses в текстовое меню: заголовок, вкладки, цвета,
выделение клиента и панели сохраняются во всех состояниях. Вывод backend
перехватывается в ограниченную память (256 KiB), без временного файла и попадания
в терминал поверх рамки. Запущенная операция завершается до выхода из Warden.
Отсутствующий env отмечается как SETUP REQUIRED; операция из TUI блокируется
до подтверждения, без перезапуска служб.

```bash
warden clients list                 # только имена, без изменений и секретов
warden clients list --json
warden clients show alice           # предпросмотр синхронизации и выдачи ссылок
warden clients show alice --run      # VLESS + обычная подписка + Happ
warden clients show all --run        # ссылки всех клиентов
warden clients add alice            # предпросмотр добавления
warden clients add alice --run
warden clients rotate alice --run    # новый UUID внутри той же подписки
warden clients remove alice --run    # отзыв доступа и удаление подписки
```

Без `--run` команды `show/add/rotate/remove` только показывают план. Для обновления
содержимого существующих подписок без смены UUID используйте `show <имя|all> --run`:
как в исходном скрипте, синхронизируются все подписки, затем показываются выбранные
ссылки. При `rotate` старый VLESS URI перестаёт работать, URL подписки остаётся
прежним; пользователь обновляет подписку в своём приложении. Для Happ выдавайте
ссылку с окончанием `/happ`. Общие параметры сервера и переименование здесь не редактируются.

В поставку включён `helpers/manage-ravelin-vless-ws-users.sh` из инфраструктурного
репозитория. Он вызывает **установленные на Ravelin**
`/usr/local/sbin/ravelin-vless-subscriptions` и, при наличии,
`/usr/local/sbin/ravelin-vless-traffic-accounting`. Их версии, правила Happ,
файлы подписок и учёт трафика установщик Warden не заменяет. Не нужно копировать
сам исходный users-скрипт на сервер отдельно.

Используется `/etc/sing-box/vless-ws.json`, inbound `vless-ws`, окружение
`/root/ravelin-vless-ws.env`. Для другого env-файла добавьте абсолютный путь
`"clients_env": "/root/другой.env"` в `/etc/warden/config.json`. Env-файл — доверенный
shell-файл администратора, как в исходном скрипте. Другой `vless` допускается для
наблюдения, но клиентские изменения отклоняются, чтобы не затронуть другой конфиг.

Если runtime env утрачен, `.env.example` не подходит. В checkout есть
`helpers/recover-clients-env.py`: он сравнивает актуальные UUID, WS-путь,
сохранённые обычные/Happ-подписки, nginx prefix и указанную политику через
**установленный** renderer подписок. Сравнение профилей игнорирует только LastUpdated.
Если параметры или политика не совпадают, восстановление отклоняется. Пример
(замените путь политики на существующий путь на своём сервере):

```bash
python3 helpers/recover-clients-env.py --policy /absolute/path/ravelin-happ-routing.json
# Только после MATCH повторите с --apply.
python3 helpers/recover-clients-env.py --policy /absolute/path/ravelin-happ-routing.json --apply
```

Сначала только чтение. `--apply` создаёт отсутствующий `/root/ravelin-vless-ws.env`
с правами 0600; существующие файлы не заменяются. UUID, токены, опубликованные
подписки и службы не меняются. Восстанавливается минимальный env для клиентских
операций, **не полный конфиг для переустановки VLESS-сервера**. При нестандартном
формате установленного renderer утилита откажет, потребуется ручная проверка.

В 0.3.2 для подтверждённого нового клиента без записи подписки можно явно добавить
`--allow-missing <имя>` (повторяется для нескольких клиентов). Исключения должны
точно совпасть с фактическим списком отсутствующих записей. Все существующие
подписки проверяются полностью; пустое хранилище и подписки без клиента
по-прежнему блокируют восстановление. Команда не создаёт подписки для исключённых
клиентов: это выполняется последующей обычной синхронизацией после восстановления env.

**Влияние операций:**

- `list` и отображение вкладки пассивны. UUID и ссылки не попадают в SQLite,
  `doctor`, журнал сборщика или автоматическое обновление экрана.
- `show --run` синхронизирует подписки, проверяет и reload-ит nginx, не меняя UUID.
- `add/rotate/remove --run` проверяют конфиг, сохраняют закрытую резервную копию,
  синхронизируют учёт и **перезапускают sing-box**, что может прервать соединения
  клиентов. Затем синхронизируют подписки и reload-ят nginx.
- Скрипт использует общую блокировку клиентов; изменения также согласованы с
  блокировкой `forpostctl` (ожидание до 30 секунд). Последнего клиента удалить нельзя.
- Перед изменением и после учёта проверяются стабильный источник `10.78.254.2`
  и сохранение существующих меток. AWG/udp2raw не перезапускаются.
- В дополнение к исходному скрипту проверяются настройки URI до изменений,
  резервные каталоги уникальны и создаются с закрытыми правами.

Выполняющуюся операцию Warden дожидается до конца: Ctrl+C не обрывает её между
записью конфига и обновлением служб. Полной транзакции между sing-box, учётом,
подписками и nginx нет. Например, ошибка подписок возможна уже после смены UUID.
При ошибке Warden возвращает ненулевой код, предупреждает о частичном применении
и не повторяет операцию автоматически. Проверьте вывод и службы до повторения;
не запускайте rotate повторно для исправления одной только подписки.

## Совместимость с текущим forpostctl

Каналы, приоритеты, `enabled/retired`, адреса и транспорт читаются из реестра v2.
ID `primary` не привязан к старому интерфейсу или определённому VPS. В деталях
показаны `udp`/`icmp`/`faketcp` и результаты `probe_details` контроллера, включая
этап `tcp`/`tls`/`http` и причину ошибки. Устаревшие результаты помечаются STALE.
Для ICMP/fakeTCP наблюдаются службы `forpost-faketcp-<интерфейс>.service`:
их историческое имя само по себе не означает транспорт fakeTCP.

Свежий handshake и работающая служба транспорта не подменяют проверку HTTPS.
Настройки буферов, MTU, ответных marks проб и отдельного сборщика инцидентов
сохраняются. Установленный WSS-транспорт читается из реестра; обновление Warden
не меняет транспорт. Обновление Warden не запускает
`forpostctl`, ремонт сети или миграцию реестра.

## Сначала посмотреть без установки

На Ravelin, из root-сессии:

```bash
git clone https://github.com/d3m10rg/warden.git /root/warden
cd /root/warden
git checkout v0.2.1
python3 -B bin/warden --demo
python3 -B bin/warden status --live
```

Demo использует синтетические данные и не читает состояние сервера. `status --live`
выполняет только чтение; не создаёт базу, не запускает службы и не отправляет пробы.
Без TTY команда без аргументов выводит текстовый статус вместо TUI.

## Установка (выполняет администратор)

Из проверенного checkout `/root/warden`:

```bash
sh install.sh
systemctl status warden-collector.service --no-pager
warden status
warden
```

Установщик копирует код в `/opt/warden`, создаёт `/usr/local/bin/warden`, настройки
`/etc/warden/config.json`, `/var/lib/warden` и **только** `warden-collector.service`.
Он выполняет `systemctl daemon-reload` и включает/запускает Warden. Службы VPN,
контроллер, Nginx, firewall и их конфигурации не изменяются. Каталог `/opt/warden`
без маркера установки не перезаписывается.

Collector опрашивает состояние приблизительно раз в 10 секунд. Скорость появляется
после двух последовательных измерений; полный час/сутки — после накопления данных.
TUI перечитывает готовый снимок из базы, не создавая дополнительных фоновых проб.
Если сборщика нет, показывается один текущий снимок; он со временем станет STALE.

```bash

warden traffic secondary --window 1h --json
warden traffic secondary --window 24h
warden traffic awg0/PEER_ID --window 1h
warden history --since 48h
warden history primary --since 2h
```

Глобальные параметры ставятся перед подкомандой:

```bash
warden --config /etc/warden/config.json status
warden --database /var/lib/warden/warden.sqlite3 history --json
```

`collect` и `collect --once` записывают **только историю Warden**; не запускайте их
параллельно службе. Файловая блокировка не допускает второго сборщика той же БД.
Коды возврата: 0 — команда выполнена (включая наблюдаемый Down в status);
1 — ручная проверка не прошла/не получила ответ; 2 — ошибка команды/предпроверки;
130 — прерывание. Подробная причина доступна в JSON.

TUI: `1–7`, Tab и горизонтальные стрелки — вкладки; вертикальные стрелки — выбор
туннеля/прокрутка; Enter — подробности; Esc — назад; PgUp/PgDn — прокрутка; q — выход.
Английские короткие статусы используются для компактного терминального отображения.

## Диагностика 0.2

Открытие вкладки и команды status/list/show остаются пассивными. Проверки не
влияют на статус controller health, приоритеты или маршруты. Их результаты
хранятся только в текущем TUI-сеансе/выводе CLI; SQLite остаётся базой наблюдений.
Нет фонового расписания, DNS-запросов, proxy, перенаправлений HTTP и установки пакетов.

```bash
warden doctor --json                         # только чтение, без адресов/секретов
warden ping secondary --scope internal       # предпросмотр, без пакетов
warden ping secondary --scope internal --run # 3 пакета, дедлайн 5 секунд
warden ping secondary --scope external --run
warden https secondary                      # предпросмотр привязки к каналу
warden https secondary --run --json          # один HTTPS target из контроллера
warden speed secondary                      # пока нет настройки — объяснит причину
warden speed secondary --run                 # 5 секунд, 5 Mbit/s, upload
warden speed secondary --seconds 5 --mbps 3 --reverse --run
```

CLI без `--run` проверяет маршрут и показывает план. Во вкладке `7 Diagnostics`
стрелки выбирают туннель; `i`/`e` — внутренний/внешний ping, `h` — HTTPS,
`s` — скорость, `d` — doctor. После предпросмотра `y` запускает проверку, `Esc`
отменяет. Обновления наблюдений продолжаются во время проверки. Выход закрывает
дочерний процесс проверки. Повторной проверки автоматически не будет.

Перед выполнением заново читаются live-данные и маршрут с source и oif.
В TUI изменение подтверждённого плана требует нового предпросмотра. Сокеты
привязаны к интерфейсу; для HTTPS также используются SOURCE, mark и probe table
установленного контроллера, проверяется unreachable default. При несовпадении —
отказ, без резервной отправки через другой канал. Конфигурация контроллера читается
как literal AST, не исполняется. Проверка HTTPS использует первый TARGETS,
проверяет сертификат/SNI и HTTP 200, бюджет 5 секунд и до 1024 байт ответа.
Это диагностика одной цели, не полный алгоритм health контроллера и не VLESS-сеанс.

Внутренний ping использует локальный адрес туннеля и peer. Внешний — публичный IP
канала через текущий физический/нетуннельный маршрут. `Reachable` означает ответ
на ICMP; `No reply` не доказывает недоступность хоста (ICMP может быть запрещён).
Показываются RTT и потери; ошибки инструмента/маршрута отделены от отсутствия ответа.

Для постоянного туннеля задайте точные цели: Warden не угадывает обязательный peer
по AllowedIPs. В существующий `/etc/warden/config.json` можно добавить раздел
(адреса ниже — примеры, **замените своими**):

```json
"diagnostics": {
  "awg0": {"internal": "10.90.0.1", "external": "192.0.2.20"},
  "secondary": {"speed_host": "10.90.1.1", "speed_port": 5201}
}
```

Для Forpost внутренний/внешний адрес уже читается из контроллера; можно явно
переопределить цели в diagnostics. HTTPS предназначен для каналов контроллера;
постоянные туннели поддерживают ping и подготовленный iperf3 без failover-управления.
Изменения diagnostics читаются при каждой проверке, перезапуск службы не нужен.

iperf3 требует **отдельно подготовленный сервер** за туннелем и установленный
локальный клиент с `--bind-dev`. Пока сервера нет, speed_host не задавайте.
Параметры: один TCP-поток, 1–10 секунд, целевая скорость 1–10 Mbit/s, upload или
`--reverse` download. По умолчанию около 3.1 MB полезной нагрузки за 5 секунд;
служебный трафик и особенности TCP добавляют расход. Это измерение при ограничении
нагрузки, не максимальная ёмкость канала. При неподдерживаемых опциях нет повторного
запуска без привязки/лимитов. Одновременно разрешена одна проверка Warden (блокировка
`/run/warden-diagnostics.lock`); сетевые проверки не запускаются из collector.

Для ping нужен iputils-ping, для скорости — iperf3. Установщик не добавляет их
автоматически; отсутствие этих опциональных инструментов не мешает наблюдению.
Doctor выдаёт allowlist состояний компонентов и наличия инструментов, без адресов,
peer ID, путей конфигурации, журналов, пользовательских имён и учётных данных.

Справочники реализации: [iperf3](https://software.es.net/iperf/invoking.html),
[iputils ping](https://github.com/iputils/iputils/blob/master/doc/ping.xml).

## Настройки и границы наблюдения

`config.example.json` содержит только отображаемые названия. `names` и `notes`
задаются по ID канала или интерфейсу; `peer_names` — по отображаемому `peer_id`.
Причина вроде блокировки провайдером — комментарий администратора, не автоматический
диагноз Warden. Изменение настроек применяется после перезапуска только сборщика:

```bash
systemctl restart warden-collector.service
```

Необязательные пути: `engine`, `registry`, `health`, `vless`, `database`, `clients_env` (абсолютные).
При другом пути БД нужно также адаптировать systemd `ReadWritePaths`. Не указывайте
общедоступные каталоги: отчёт содержит сетевые адреса и операционную информацию.

- `Active` — выбранный маршрут, не гарантия исправности. `Active + Degraded` допустим
  во время подтверждения отказа. Числовой rank для v1 неизвестен (`null`): Warden не
  выдумывает приоритеты, отсутствующие в конфигурации старого контроллера.
- `Observed` у постоянного туннеля означает наличие свежего handshake хотя бы у
  одного peer. Какие peer обязательны, Warden не угадывает. Связность проверяется вручную.
- Свежесть handshake по умолчанию 180 секунд — диагностический признак; Forpost
  оценивается по HTTPS-результатам контроллера с возрастом не более 30 секунд.
- Состояние контроллера проверяется с учётом Linux boot ID и монотонного времени.
  Снимки старше 30 секунд помечены STALE; время перед началом наблюдения неизвестно.
- Направления RX/TX относительно Ravelin. Интерфейс и peer — разные источники
  счётчиков; их нельзя суммировать между собой. Трафик туннеля не равен трафику VLESS.
- Объёмы вычисляются по разностям счётчиков. Пропуски >30 секунд, reboot, смена
  идентичности или endpoint, скачок часов и сброс счётчика дают разрыв, а не ноль.
  Неполное покрытие показывается в процентах; дробная граница окна оценивается
  пропорционально интервалу и помечается `boundary_estimated`.
- История handshake — обнаруженные изменения последнего timestamp, не перехват
  каждого обмена. Журнал службы читается вперёд, до 500 записей за цикл; Warden
  сохраняет только события переключения. Курсор продвигается и по обычным сообщениям
  службы. При отсутствии/ротации журнала полнота не гарантируется и отмечается
  предупреждением. Изменения роли между опросами могут быть пропущены.
- Полный клиентский сеанс VLESS и TLS Nginx не проверяются. Наличие listener и
  запущенной службы не заменяет такую проверку.

## Исправление журнала в 0.2.1

Старое сочетание `journalctl --grep` и `-n 500` включало обратный порядок выдачи;
редкие переключения не ограничивали объём просмотра обычных сообщений. Новый
читатель использует `-n +500` без grep, а фильтрует сообщения в Python. Это
ограничивает размер порции записями службы, а не числом найденных переключений.

После обновления выполняется один последовательный просмотр доступного журнала за
48 часов. Он идёт порциями вместе с обычными циклами, без ускоренного опроса.
`Catching up` означает, что история ещё догружается; текущие статусы обновляются.
При большом журнале догрузка может занять десятки минут. Существующие записи и
трафик сохраняются, дубликаты переключений отсеиваются по исходному cursor.

Таймаут, ошибка команды, повреждённая запись и восстановление cursor отображаются
отдельно. После ошибки повторное чтение откладывается на 60 секунд с увеличением
до 10 минут, сбор остальных наблюдений продолжается. Лимит памяти остаётся 128 MiB.
`doctor --json` показывает `collector_journal` из сохранённого снимка и его возраст;
сам doctor не запускает просмотр журнала. `observation_warnings` относится только
к отдельному live-чтению компонентов, а не к полноте истории переключений.

Потребление cgroup включает файловый кэш; близость MemoryCurrent к MemoryMax сама
по себе не доказывает утечку Python. После догрузки нужно сравнить прирост
`memory.events:max`, показатели anon/file и сообщения Warden. Снижение кэша не
обещается немедленно после установки; чужие журналы и системный кэш не очищаются.

Семантика параметров: [официальная документация journalctl](https://github.com/systemd/systemd/blob/v257/man/journalctl.xml).

## История, нагрузка и отказ Warden

Сборщик пишет один актуальный JSON-снимок, компактные строки счётчиков и события
в SQLite WAL. Измерения и события удаляются по возрасту 48 часов приблизительно
раз в минуту во время работы сборщика. Существующий journal и чужие БД не очищаются.
База повторно использует свободные страницы; размер файла не обязан уменьшаться.
Основная БД ограничена 256 MiB при стандартной странице 4 KiB; WAL имеет отдельный
лимит сохраняемого журнала 8 MiB (во время транзакции может временно превышаться).

Служба имеет низкий CPU/I/O-приоритет, CPUQuota=20%, MemoryMax=128M, запрет записи
в системные файлы и запрет AF_INET/AF_INET6. AF_UNIX/AF_NETLINK оставлены для systemd,
`ss`, `ip`, AWG/WG. Это ограничители, **не результаты измерения нагрузки на Ravelin**.
Ошибка/переполнение БД остановит сборщик с видимой ошибкой; systemd попробует его
перезапустить. VPN и failover продолжают работу независимо, `status --live` доступен.

## Обновление и возврат версии

Автообновления нет. Сначала прочитайте изменения релиза; затем из `/root/warden`:

CI создаёт тег `v<версия>` для проверенного коммита main после успешных тестов;
существующие теги никогда не перемещаются. Это публикация версии в GitHub,
а установка на сервер всегда остаётся ручной.

```bash
git fetch --tags origin
git checkout <проверенный-тег>
sh install.sh
warden --version
systemctl status warden-collector.service --no-pager
```

Установщик сохраняет `/etc/warden/config.json` и БД, перезапуская только Warden.
Возврат к предыдущему **совместимому со схемой БД** тегу — той же процедурой.
Перед возвратом на 0.1 удалите добавленный раздел `diagnostics` из config.json:
старая версия отклоняет неизвестные поля; остальные настройки/БД сохраните.
Перед возвратом на 0.2 удалите `clients_env`, если добавляли его вручную.
Схема БД 0.1/0.2/0.3 имеет версию 1; неизвестная версия отклоняется без автоматической
миграции. Прерванную установку повторите из целого проверенного checkout; до этого
сборщик может оставаться остановленным. Файлы VPN восстанавливать не требуется.

Временное отключение Warden:

```bash
systemctl disable --now warden-collector.service
```

## Проверка перед использованием

```bash
python3 -B -m unittest discover -s tests -v
sh -n install.sh
sh -n helpers/manage-ravelin-vless-ws-users.sh
```

GitHub Actions выполняет тесты на Linux/Python 3.9 и 3.13, curses в псевдотерминале,
проверку unit, один пассивный цикл сборщика и реальные route/mark/guard/ping
в отдельном Linux network namespace без доступа к сети Ravelin. Дополнительно
проверяется последовательное чтение более 500 записей настоящего journald в CI. Результат CI доступен во вкладке Actions.
Клиентский backend проверяется на временных файлах с подставными службами:
добавление/ротация/удаление, сохранение маршрутизации, ошибки проверки/перезапуска/
подписок, блокировка, защита источника и меток. Настоящие nginx/sing-box и
установленный helper подписок эти тесты не запускают. TUI проверяет
вкладку клиентов, форму имени, подтверждение, захват результата и запрет выхода
во время операции через Linux PTY.
Испытания на действующем Ravelin и измерение его нагрузки выполняет владелец после
установки. Порядок: `status --live` → установка → два цикла → сверка маршрута и
счётчиков → наблюдение нагрузки → остановка Warden и проверка независимости VPN.

Репозиторий не содержит конфигураций пользователей, приватных ключей, токенов,
реальных публичных endpoint и дампов серверов. В demo используются тестовые адреса.
